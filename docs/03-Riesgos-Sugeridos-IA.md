# Riesgos iniciales sugeridos por IA — clasificación y justificación

Actividad de la semana: pedirle a la IA que identifique riesgos iniciales del sistema actual, describiéndolo brevemente, y luego clasificar cada riesgo como **Válido / Irrelevante / Genérico / Falso**, justificando con base en el sistema real que el equipo ya ejecuta.

## Descripción breve del sistema entregada a la IA

> CookSmart es una plataforma web con un frontend HTML/CSS/JavaScript que se comunica con una API propia en Node.js/Express. La persistencia actual se realiza en PostgreSQL, desplegado mediante Docker Compose junto con la API y Adminer. El backend está organizado como un monolito modular por capas: routes → controllers → services → repositories → PostgreSQL. La autenticación de la API utiliza JWT y bcrypt. El acceso del frontend a los datos se realiza a través de la API; el frontend no se conecta directamente a PostgreSQL. El sistema actual ya cuenta con pruebas de rendimiento con k6: un diagnóstico concentrado de `GET /api/recetas` y un recorrido autenticado que cubre login, perfil, recetas, detalle, catálogos, favoritos, historial e inventario. El proyecto es desarrollado por un equipo pequeño de estudiantes y se encuentra en una fase de validación de arquitectura y calidad.

## Riesgos propuestos por la IA y veredicto del equipo

| # | Riesgo propuesto por la IA | Veredicto | Justificación contra el sistema real |
|---|---|---|---|
| 1 | La comunicación entre la API y PostgreSQL puede convertirse en un cuello de botella bajo concurrencia, especialmente porque todas las operaciones de persistencia pasan por la misma API y el mismo servicio de base de datos. | **Válido** | Es coherente con la arquitectura actual y con la prioridad técnica del equipo sobre la comunicación API → PostgreSQL. El recorrido completo de k6 con 50 VUs presentó P95 global de 9,72 s, mientras que el diagnóstico aislado de `GET /api/recetas` presentó P95 de 232,94 ms. La diferencia indica que el comportamiento bajo un recorrido concurrente completo merece análisis por capas. El resultado no permite atribuir toda la latencia directamente a PostgreSQL, pero sí justifica investigar esta comunicación y el acceso a datos. |
| 2 | El endpoint de autenticación puede convertirse en el principal punto de degradación de rendimiento bajo concurrencia debido al coste de verificación de contraseñas con bcrypt. | **Válido** | El riesgo está directamente relacionado con el comportamiento medido. En el recorrido completo de k6, el P95 de login fue de 17,93 s, muy superior al P95 de los demás endpoints. Como el login utiliza bcrypt, este componente debe analizarse junto con el pool de conexiones, consultas y demás lógica del servicio antes de atribuir la causa exclusivamente a una sola capa. |
| 3 | La ausencia de pruebas automatizadas puede permitir que cambios en controllers, services o repositories rompan endpoints existentes sin ser detectados antes de una entrega. | **Válido** | El proyecto cuenta con validaciones manuales y experimentos de rendimiento con k6, pero eso no sustituye una suite automatizada de pruebas unitarias o de integración que se ejecute de forma repetible. En una arquitectura por capas, un cambio en una capa puede afectar a las siguientes; sin pruebas automatizadas, aumenta el riesgo de regresiones funcionales. |
| 4 | Las reglas de dependencia de la arquitectura por capas pueden degradarse con el tiempo si controllers, services o repositories comienzan a acceder directamente a capas que deberían estar encapsuladas. | **Válido** | Es un riesgo específico de la arquitectura actual. El diseño establece la dirección routes → controllers → services → repositories → PostgreSQL. Si se permite acceso directo desde controllers a la base de datos o desde routes a repositories, se pierde parte del aislamiento que justifica la arquitectura por capas. El ADR-002 define estas fronteras y propone automatizarlas posteriormente mediante una fitness function. |
| 5 | La existencia de Adminer junto al contenedor de PostgreSQL aumenta el riesgo de exposición administrativa si el entorno Docker se publica o se configura de forma insegura. | **Válido** | Adminer forma parte del entorno actual y proporciona una interfaz administrativa para PostgreSQL. En desarrollo es útil, pero representa una superficie administrativa adicional. El riesgo depende de cómo se exponga el entorno; no implica que exista actualmente una vulnerabilidad pública, sino que debe controlarse para evitar que una herramienta de administración quede accesible en un entorno no destinado a desarrollo. |
| 6 | La pérdida del volumen de PostgreSQL puede provocar pérdida de datos si no existe un mecanismo externo de backup o recuperación. | **Válido** | PostgreSQL es actualmente la persistencia principal del sistema y el despliegue utiliza un volumen Docker. La arquitectura actual depende de esa persistencia para los datos de la aplicación. Por tanto, la pérdida o corrupción del volumen constituye un riesgo de disponibilidad e integridad de datos si no existe una estrategia adicional de respaldo. |
| 7 | La ausencia de pruebas de carga prolongadas impide concluir que el sistema cumple el requisito de disponibilidad durante periodos largos de operación. | **Válido** | Las pruebas actuales de k6 son útiles para observar comportamiento bajo carga, pero el diagnóstico dura 20 s y el recorrido completo también se ejecuta durante una ventana corta. Esto no demuestra por sí solo un requisito de disponibilidad de larga duración. Se necesita un experimento específico de duración y disponibilidad para realizar esa comprobación. |
| 8 | El rendimiento observado en `GET /api/recetas` en una prueba aislada puede ocultar problemas que solo aparecen cuando un usuario ejecuta varias operaciones autenticadas consecutivamente. | **Válido** | Ya existe evidencia concreta de esta diferencia. `diagnostico.js` obtuvo P95 de 232,94 ms con 50 VUs y 6.349 solicitudes, mientras que `load-test.js`, que ejecuta un recorrido completo, obtuvo P95 global de 9,72 s. Por ello, el rendimiento de un endpoint aislado no debe utilizarse como representación suficiente del rendimiento de toda la experiencia de usuario. |
| 9 | La falta de límites de intentos o rate limiting en el login puede permitir que un atacante realice numerosos intentos de autenticación. | **Válido** | Es un riesgo de seguridad directamente relacionado con un endpoint expuesto del sistema actual. El login recibe credenciales y constituye un punto que debe protegerse contra abuso automatizado. El riesgo debe validarse revisando la implementación actual del endpoint y, si no existe control de frecuencia, incorporarlo como medida de seguridad. |
| 10 | El uso de `innerHTML` para representar datos de recetas o ingredientes puede introducir XSS si contenido controlado por usuarios termina en el DOM sin escape o sanitización adecuada. | **Válido** | Es un riesgo específico de la interacción entre el frontend actual y los datos que entrega la API. El uso de `innerHTML` no es automáticamente una vulnerabilidad, pero sí requiere revisar si los valores insertados están controlados o sanitizados. Si datos de usuario pueden alcanzar ese flujo sin tratamiento, existe riesgo de XSS almacenado o reflejado según el caso concreto. |
| 11 | Centralizar toda la persistencia en PostgreSQL impide escalar horizontalmente el sistema porque una única base de datos constituye un punto compartido de acceso a datos. | **Genérico** | La existencia de una única instancia de PostgreSQL es una característica real del despliegue actual, pero afirmar que necesariamente impide escalar horizontalmente es demasiado amplio. El sistema es un proyecto académico de pequeña escala y la prueba actual no demuestra que la base de datos sea el límite absoluto de escalabilidad. El riesgo concreto es la dependencia de una única instancia para persistencia y su capacidad bajo carga, no una imposibilidad general de escalamiento. |
| 12 | La arquitectura monolítica hará que cualquier cambio pequeño en una funcionalidad requiera desplegar todo el sistema y por ello será imposible evolucionar el proyecto de forma independiente por módulos. | **Genérico** | El sistema actual sí es un monolito modular, pero los módulos están separados lógicamente mediante capas y dependencias dirigidas. La afirmación de que cualquier cambio impedirá evolucionar módulos es una generalización sobre los monolitos. Puede existir acoplamiento, pero debe demostrarse mediante dependencias concretas del código, no asumirse únicamente por el estilo arquitectónico. |
| 13 | El uso de Docker garantiza que el sistema tendrá el mismo rendimiento en cualquier máquina del equipo. | **Falso** | Docker ayuda a reproducir versiones y configuración de los servicios, pero no garantiza el mismo rendimiento. Los resultados de k6 dependen también de recursos de CPU, memoria, disco, red, configuración del host y carga concurrente. Por ello, los resultados deben asociarse a las condiciones concretas del experimento. |
| 14 | PostgreSQL eliminará automáticamente los problemas de rendimiento que existían cuando se utilizaba Firebase Realtime Database. | **Falso** | Cambiar el mecanismo de persistencia no garantiza eliminar los problemas de rendimiento. El resultado de k6 demuestra que el endpoint aislado de recetas puede responder con P95 de 232,94 ms, pero el recorrido completo todavía presenta P95 global de 9,72 s. La migración cambia la arquitectura de persistencia; no constituye por sí sola una garantía de rendimiento. |
| 15 | El uso de JWT significa que el sistema ya está protegido contra todos los ataques relacionados con autenticación. | **Falso** | JWT proporciona un mecanismo para transportar y validar identidad/autorización, pero no elimina riesgos como contraseñas débiles, fuerza bruta, mala gestión de secretos, expiración incorrecta, validación defectuosa o autorización insuficiente. La seguridad depende de la implementación completa del flujo de autenticación y autorización. |

## Aprendizajes sobre supuestos y contexto

- **La descripción del sistema cambia los riesgos que la IA identifica.** Al describir el sistema actual como frontend → API Node/Express → PostgreSQL, los riesgos relevantes se concentran en las fronteras y componentes que realmente existen: autenticación, comunicación API → PostgreSQL, acceso a datos, dependencias entre capas, persistencia y rendimiento.

- **Los resultados de k6 permiten distinguir entre un riesgo hipotético y un comportamiento observado.** La diferencia entre el diagnóstico aislado de `GET /api/recetas` (P95 de 232,94 ms) y el recorrido completo (P95 global de 9,72 s) demuestra que la carga compuesta debe analizarse de manera independiente.

- **Un resultado de rendimiento no identifica por sí solo la causa.** El P95 de login de 17,93 s señala un punto de degradación importante, pero no permite concluir que bcrypt, PostgreSQL, la red o el código de servicio sea por sí solo responsable. El siguiente paso debe ser instrumentar y medir cada capa.

- **Los riesgos arquitectónicos deben relacionarse con las fronteras reales.** En el sistema actual, la comunicación API → PostgreSQL es una frontera especialmente importante porque los repositories concentran el acceso a datos. Por eso, problemas de pool, consultas, conexiones o tiempos de acceso pueden afectar a varias funcionalidades simultáneamente.

- **La clasificación "Genérico" es útil para separar afirmaciones generales de riesgos concretos.** La existencia de una única instancia de PostgreSQL y el uso de un monolito son hechos reales, pero no basta con ellos para afirmar automáticamente que el sistema no puede escalar o evolucionar.

- **La clasificación "Falso" también requiere contrastar el funcionamiento real.** Docker no garantiza rendimiento uniforme y PostgreSQL no garantiza por sí solo eliminar problemas de rendimiento. Las conclusiones deben derivarse de las condiciones de ejecución y de las mediciones disponibles.

- **Los riesgos de seguridad deben mantenerse separados de las conclusiones de rendimiento.** La ausencia de rate limiting o un posible uso inseguro de `innerHTML` son cuestiones de seguridad que requieren validaciones específicas, mientras que los resultados de k6 sirven principalmente para estudiar rendimiento bajo carga.

## Conclusión

El ejercicio muestra que la utilidad de una lista de riesgos generada por IA depende directamente del contexto que recibe. Para el sistema actual de CookSmart, los riesgos más directamente sustentados son los relacionados con la comunicación API → PostgreSQL, la latencia del login, la ausencia de pruebas automatizadas, el mantenimiento de las fronteras entre capas, la persistencia de PostgreSQL, la disponibilidad y determinados controles de seguridad.

La clasificación no pretende priorizar los riesgos ni establecer cuál es más importante. Su objetivo es comprobar si cada propuesta de IA corresponde realmente al sistema que el equipo ejecuta y si existe evidencia suficiente para aceptarla como riesgo del proyecto.
